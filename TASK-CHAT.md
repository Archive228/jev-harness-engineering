# Задача: живой чат с харнессом

Собрать интерактивный чат поверх существующего `jev-harness-lab`. Пользователь пишет в поле, харнесс реально работает, ответ приходит потоком, внутренности видны справа.

Сейчас есть `jev-console.html` — он **проигрывает записанные прогоны**. Нужно другое: **живой прогон по тому, что ввёл человек**.

---

## 1. Что должно получиться

Одна страница, розовый однобитный стиль как в `jev-console.html` (палитра, шрифты и классы уже есть, переиспользовать).

Внизу поле ввода. Сверху лента сообщений. Справа четыре окна, которые обновляются **во время** работы: `JEV`, `REQUIREMENTS`, `POLICY`, `METERS`.

Два сценария в одном поле.

### Сценарий A — спросить Jev (мгновенный)

Человек пишет обычный текст, например обращение в поддержку. Текст уходит в `state`, к нему задаются вопросы, ответ приходит за ~1 секунду.

```
я  ▸ В Safari экспорт PDF падает. В Chrome тот же документ выгружается.
jev ◂ category = export        p(export)=1.00
jev ◂ impact = 1.00            уровень «есть обходной путь»
jev ◂ has_workaround = 0.95
    confidence 1.00 = (4×1.00−1)/3 · usage 746 in / 79 out · 0.98 s
```

По умолчанию задаются три вопроса из статьи (`category` / `impact` / `has_workaround`). Свой вопрос — командой:

```
/ask noul В обращении названа конкретная версия браузера?
/ask choice критично,терпимо,неважно Насколько это срочно?
```

Вопрос строится на клиенте, уходит на сервер, сервер зовёт `Judge.ask`.

### Сценарий B — запустить цикл (длинный, потоковый)

```
/run backend Поиск должен находить запись по слову из описания
```

Запускается настоящий цикл харнесса на выбранном дефекте. В ленту потоком падают те же строки, что сейчас в реплее: `policy`, `jev ▸/◂`, `exec ▸/◂`, `worker`, `■ END`. Правые окна обновляются на каждом событии.

Сценарии: `ui`, `backend`, `both` — это существующие seed-проекты в `runs/jev-codex-eval-2026-09-20/*-seed/project`. Текст после названия сценария кладётся в `task.md` как задание воркеру (это уже умеет флаг `--task`).

### Команды

| команда | что делает |
|---|---|
| `/ask <тип> [варианты] <вопрос>` | свой вопрос к последнему `state` |
| `/run <ui\|backend\|both> [текст задачи]` | полный цикл с Codex |
| `/run demo` | цикл на фикстурах, без ключей и без Codex |
| `/stop` | прервать текущий прогон |
| `/policy confidence <0..1>` | поменять `min_choice_confidence` для следующего прогона |
| `/clear` | очистить ленту |

## 2. Бэкенд

Новый файл `jev-harness-lab/chat_server.py`. **Только стандартная библиотека** — в репозитории нет внешних зависимостей, это условие сохраняем.

```
python3 chat_server.py --port 8770
```

### Эндпоинты

**`GET /`** — отдаёт `chat.html`.

**`POST /api/ask`**

```json
{ "state": "текст или объект",
  "questions": { "category": {"type":"choice","instructions":"...","criteria":{...}} } }
```

Ответ: то, что вернул `Judge.ask`, плюс посчитанное:

```json
{ "answers": {...}, "usage": {...}, "elapsed_ms": 984,
  "derived": { "category": { "n": 4, "p_max": 1.0, "need_for_threshold": 0.73,
                             "confidence_formula": "(4×1.00−1)/3" } } }
```

`need_for_threshold` считается как `(c·(n−1)+1)/n`, где `c` — текущий `min_choice_confidence`. Это то самое число, которое рисуется меткой на полоске.

**`GET /api/run?scenario=backend&task=...&run_id=...`** — поток **SSE** (`text/event-stream`). SSE, а не вебсокет: односторонний поток, хватает `http.server`, ничего ставить не надо.

Каждое событие: `data: {"t":"...", ...}\n\n`

| `t` | поля | когда |
|---|---|---|
| `boot` | `snapshot`, `case`, `policy`, `worker_kind` | старт |
| `policy` | `action`, `reason`, `check_id`, `rule` | каждое решение |
| `jev` | `file`, `model`, `rows[]`, `usage`, `need`, `elapsed_ms` | каждый вызов Jev |
| `exec` | `check_id`, `exit_code`, `elapsed_ms`, `snapshot`, `snapshot_after`, `detail` | каждая проверка |
| `worker` | `claim`, `elapsed_ms` | каждая итерация Codex |
| `report` | `criteria[]`, `meters{checks,jev,iter,sec}` | после пересборки отчёта |
| `end` | `status`, `reason`, весь `result.json` | конец |
| `error` | `message`, `where` | любая ошибка |

**`POST /api/abort`** — `{"run_id":"..."}`, выставляет флаг, цикл останавливается на ближайшей проверке лимитов.

### Хуки в существующий код

Правки минимальные, цикл не переписывать.

В `run.py`, класс `Lab`:

1. В `__init__` принять необязательный `emit=None`, сохранить в `self.emit`.
2. Завести `self._emit(t, **kw)` — если `self.emit` задан, вызвать; иначе тихо выйти. Никогда не ронять прогон из-за ошибки в `emit`: обернуть в `try/except`.
3. `record_decision()` — после записи в `events.jsonl` позвать `self._emit("policy", **action)` и `self._emit("report", criteria=..., meters=...)`.
4. `ask()` — после `self.judge.ask(...)` позвать `self._emit("jev", ...)`.
5. `check()` — после `run_check(...)` позвать `self._emit("exec", **record)`.
6. Шаг воркера — `self._emit("worker", claim=...)`.
7. `finish()` — `self._emit("end", **result)`.
8. В `remaining()` добавить проверку флага отмены: если выставлен, кинуть `LimitError("aborted")`.

Сервер запускает `Lab` **в отдельном потоке**, `emit` кладёт события в `queue.Queue`, обработчик SSE читает очередь и пишет в сокет. Один активный прогон на сервер — этого достаточно, второй запрос получает `409`.

## 3. Безопасность

Это самая важная часть, не пропускать.

- **Введённый текст — это данные, никогда не команда.** Он попадает только в `state` для Jev или в `task.md` для воркера. Никогда не в `subprocess`, никогда в `eval`.
- Выполняются **только зарегистрированные проверки** из `checks.json` по их ID. Ответ модели сверяется с реестром — это уже сделано в `run.py`, не ослаблять.
- `/policy` принимает **только** `min_choice_confidence` и `scope_threshold`, только `float` в диапазоне `0..1`. Остальные ключи игнорировать.
- Сервер слушает **только `127.0.0.1`**. Никакого `0.0.0.0`.
- `TYPESAFE_API_KEY` читается из окружения сервера и **никогда не отдаётся в браузер** и не передаётся в процесс воркера.
- Ограничить длину входа: `state` не больше 20 000 символов, иначе `413`. У Jev лимит 32k токенов на `state` с самым длинным вопросом.
- Рабочая копия проекта — только внутри `runs/<id>/project`, как сейчас.

## 4. Фронтенд

Новый `chat.html`, генерится из `scripts/build-chat.cjs` (по образцу `build-console.cjs`, чтобы стиль не разъехался).

- Ленту, полоски вероятностей, метку порога, окна `REQUIREMENTS` / `POLICY` / `METERS` — **брать из `jev-console.html` как есть**, функции `mind()`, `board()`, `meters()`, `emit()` уже написаны и работают.
- Композер внизу: `textarea` + кнопка `send`, отправка по `Cmd+Enter`, `Shift+Enter` — перенос строки.
- Во время прогона: кнопка `send` становится `stop`, поле блокируется.
- Автоскролл ленты вниз, но если человек проскроллил вверх — не дёргать.
- Индикатор ожидания: мигающий квадратный курсор `▮` в конце последней строки, он уже есть в CSS как `.cur`.
- Переподключение SSE при обрыве: `EventSource` делает это сам, но нужно дедуплицировать по индексу события, иначе лента задвоится.

## 6. Чего не делать

- Не переписывать цикл `Lab.run()`. Только хуки.
- Не тащить Flask, FastAPI, socket.io. Только стандартная библиотека.
- Не давать модели выбирать shell-команды. Реестр закрытый.
- Не делать «умный» разбор свободного текста в требования. Контракт приёмки остаётся из `checks.json`, текст идёт воркеру как задание.
- Не хранить ключ в `localStorage` и не показывать его в интерфейсе.

## 7. Порядок работы

1. Хуки `emit` в `run.py` + тест на них. Убедиться, что без `emit` всё работает как раньше.
2. `chat_server.py`: сначала `/api/ask`, он самый простой и сразу даёт живой результат.
3. `chat.html` с одним только сценарием A.
4. SSE и `/api/run`.
5. `/stop`, `/policy`, дедупликация при переподключении.

Первые три пункта дают работающий продукт сами по себе.
