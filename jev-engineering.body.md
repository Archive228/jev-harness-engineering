## 1. Что Jev делает с вашим текстом

Представьте обращение:

> В Safari экспорт PDF завершается ошибкой. В Chrome тот же документ экспортируется. Сейчас пользуюсь Chrome, но хочу вернуть экспорт в Safari.

Приложению нужны три вещи: категория проблемы, её влияние на работу и наличие обходного пути. Jev получает текст и вопросы, а возвращает значения, которые программа может использовать дальше. Разработчик задаёт допустимые варианты и смысл критериев. [Интерфейс TypeSafe](https://docs.typesafe.ai/introduction).

![Как устроен вызов Jev: состояние и вопросы превращаются в типизированные ответы](./assets/01-jev-interface.svg)

В запросе три основных поля:

```python
payload = {
    "model": "jev-1.13.0",
    "state": ticket,
    "questions": questions,
}
```

В `state` вы кладёте материал для оценки: сообщение, фрагмент документа, результаты инструментов или небольшой объект JSON. В `questions` перечисляете вопросы к этому материалу, в `model` указываете версию Jev. В статье фиксируем `jev-1.13.0`; перед собственным экспериментом проверьте её доступность. Алиас `jev-latest` удобен для знакомства, но может начать указывать на другую версию. В документации английский указан как наиболее сильный язык модели. В `judge.py` вопросы английские; `first_call.py` повторяет русские формулировки статьи. Мы проверили оба варианта, а размеченные наборы включают русский и английский текст. Для ваших данных всё равно нужна отдельная проверка. [Модели](https://docs.typesafe.ai/models).

У запроса есть жёсткие границы: 64k токенов на весь запрос и 32k на `state` вместе с самым длинным вопросом, не более 255 вариантов в Choice и от двух до десяти уровней в Score. Входные токены стоят $0.042 за миллион, выходные не тарифицируются, поэтому дополнительный вопрос к уже отправленному `state` почти ничего не добавляет к счёту.

Дальше работает обычный код: кладёт обращение в очередь, сортирует результаты или запускает разрешённую проверку. Jev сам не открывает браузер, не выполняет shell-команду и не исправляет файл: эти возможности предоставляет окружающее приложение.

Генеративные LLM тоже могут возвращать структурированный JSON. Практический вопрос в другом: насколько хорошо конкретный узел с Jev решает вашу задачу при сопоставимой стоимости. Для ответа нужно сначала точно определить этот узел.

## 2. Три примитива на одном обращении

У Jev три основных вида вопросов. Выбор между ними зависит от того, какой ответ нужен программе.

![Choice выбирает вариант, Score оценивает положение на шкале, Noul отвечает на утверждение](./assets/02-three-primitives.svg)

### Choice: выбрать один вариант

Для категории обращения подходят варианты без порядка: экспорт, аккаунт, оплата, другое.

```python
category_question = {
    "type": "choice",
    "instructions": "К какой категории относится основная проблема?",
    "criteria": {
        "export": "Создание или скачивание экспортируемого файла",
        "account": "Вход в аккаунт и доступ к нему",
        "payment": "Списания, счета и платежи",
        "other": "Ни одна из перечисленных категорий не подходит",
    },
}
```

В ответе `choice` содержит выбранный вариант, `probabilities` даёт распределение по вариантам, а `confidence` показывает, насколько это распределение сосредоточено.

Важная деталь, которую легко пропустить: `confidence` не отдельный сигнал, а функция от `probabilities`. Для `n` вариантов документация сводит её к `(n × p_max − 1) / (n − 1)`. Мы проверили формулу на всех 161 сохранённом в комплекте ответе Choice и Score: максимальное расхождение 0.015, то есть округление до сотых. Порог `confidence = 0.60` на трёх вариантах означает ровно требование `p_max >= 0.73`.

Сохраняйте оба поля. Распределение говорит, кто был вторым; `confidence` удобнее для порога. Читать `confidence` как измеренную вероятность правильного ответа на ваших данных нельзя. [Choice](https://docs.typesafe.ai/primitives/choice), [Confidence](https://docs.typesafe.ai/confidence).

Описание `other` даёт модели допустимый выход, если список не покрывает обращение. Без него победитель всё равно найдётся, пусть и среди неподходящих вариантов.

### Score: поместить случай на описанную шкалу

Теперь оценим, насколько проблема мешает работе:

```python
impact_question = {
    "type": "score",
    "instructions": "Как проблема влияет на выполнение задачи?",
    "criteria": [
        "Косметический дефект; задача выполняется обычным способом",
        "Функция нарушена, но указан рабочий обходной путь",
        "Задача заблокирована; рабочего обходного пути нет",
    ],
}
```

Позиции массива задают уровни `0`, `1`, `2`. В ответе есть `score`, распределение `probabilities`, обратная расшифровка уровней `legend` и `confidence`. Дробный `score` получается как сумма уровней, взвешенная их вероятностями.

На нашем обращении вся масса ушла на уровень 1, поэтому `score` вышел ровно `1.0`: обход назван в тексте прямо, спорить не о чем. Дробное значение появляется там, где спорен сам случай. Возьмите обращение вида «Экспорт PDF падает. Коллега говорит, что в другом браузере работает, но поставить второй браузер я не могу» и прогоните его через тот же `first_call.py`: часть массы должна остаться на уровне 1, часть уйти на уровень 2. Значение `score` относится к вашей шкале и не означает долю пострадавших пользователей. [Score](https://docs.typesafe.ai/primitives/score).

Наши уровни описывают наблюдаемые ситуации. «Плохо», «очень плохо» и «катастрофически плохо» оставили бы гораздо больше пространства для разных трактовок. Перед применением к реальным обращениям стоит отдельно решить, считается ли переход в другой браузер приемлемым обходом для вашей аудитории.

### Noul: оценить конкретное утверждение

Третий вопрос:

```python
workaround_question = {
    "type": "noul",
    "instructions": "Указан ли в обращении рабочий обход проблемы?",
    "criteria": {
        "true": "Автор прямо сообщает, что выполняет ту же задачу другим способом",
        "false": "Рабочий обход не указан; есть лишь предположение или его нет совсем",
    },
}
```

Поле `noul` содержит число от 0 до 1, вероятность ответа «да»; около `0.5` означает неопределённость между «да» и «нет». Отдельного поля `confidence` у Noul нет. [Noul](https://docs.typesafe.ai/primitives/noul).

Здесь мы проверяем содержание сообщения. Мы не проверяем фактическую работоспособность Chrome: для этого понадобился бы другой источник сведений. Такая точность формулировки пригодится в сборке отчёта о работе агента.

Все три вопроса можно отправить с одним `state`:

```python
questions = {
    "category": category_question,
    "impact": impact_question,
    "has_workaround": workaround_question,
}
```

Внутри такого запроса вопросы оцениваются независимо. Ответ на `category` не становится входом для `impact`. Если первый ответ определяет варианты следующего вопроса, соберите новый запрос. Проверку согласованности нескольких ответов также делает приложение. [Примитивы](https://docs.typesafe.ai/primitives).

Эту же организацию рекомендуют [официальные примеры и skill TypeSafe](https://github.com/typesafe-ai/skills): независимые вопросы задаём вместе, а после нового наблюдения собираем следующий запрос. ID вроде `has_workaround` служит для сопоставления ответа с вопросом; весь смысл вопроса нужно выразить в `instructions` и `criteria`.

Удобное правило для своего проекта: **варианты → Choice; шкала → Score; конкретное утверждение → Noul**.

## 3. Где этот интерфейс полезен

Одинаковая форма вызова позволяет строить разные продукты. Меняются материал, вопросы и действие после ответа.

- **Поддержка.** Сообщение → Choice категории и Score влияния → очередь обращений с понятным приоритетом. Разобранный выше пример можно превратить в первый самостоятельный инструмент.
- **Поиск по документам.** Запрос и найденный фрагмент → Noul о том, отвечает ли фрагмент нужному условию → порядок результатов. Jev оценивает то, что вы передали; поиск кандидатов остаётся отдельной частью приложения. [Официальный cookbook reranking](https://docs.typesafe.ai/cookbooks/rerank_typesafe).
- **Выбор модели или инструмента.** Задача и описания доступных исполнителей → Choice → вызов выбранного исполнителя. Такой способ интеграции рассматривается в [материале LangChain](https://www.langchain.com/blog/building-a-harness-with-jev).
- **Отбор контекста.** Текущая задача и кандидат в память → Noul о его полезности → включение в следующий контекст. Для первого опыта удобно сохранять решения рядом с действующим отбором и проверять пропуски вручную.
- **Действия в браузере.** Состояние страницы и доступные действия → выбор действия и цели → выполнение браузерным инструментом. Посмотреть конкретную реализацию можно в [browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast).
- **Проверка coding agent.** Требование и результаты работы → оценка связи свидетельства с требованием, затем выбор диагностики → следующая проверка или исправление. Эту ветку мы соберём полностью.

Это карта применений, а не перечень встроенных функций Jev. Пользовательскую пользу создаёт вся цепочка: хорошие входные данные, подходящий вопрос, разумное действие и проверка результата.

```python
import json
import os
from urllib.request import Request, urlopen

ticket = (
    "В Safari экспорт PDF завершается ошибкой. "
    "В Chrome тот же документ экспортируется. "
    "Сейчас пользуюсь Chrome, но хочу вернуть экспорт в Safari."
)
payload = {
    "model": "jev-1.13.0",
    "state": ticket,
    "questions": questions,
}
request = Request(
    "https://api.typesafe.ai/v1/systemone",
    data=json.dumps(payload, ensure_ascii=False).encode("utf-8"),
    headers={
        "Authorization": "Bearer " + os.environ["TYPESAFE_API_KEY"],
        "Content-Type": "application/json",
    },
    method="POST",
)
with urlopen(request, timeout=30) as response:
    result = json.load(response)

answers = result["answers"]
print(answers["category"]["choice"])
print(answers["impact"]["score"])
print(answers["has_workaround"]["noul"])
```

Русский `first_call.py` действительно выполнился и напечатал `export`, `1.0`, `0.95`. Один запрос занял около 0,98 секунды с сетевыми накладными расходами; API сообщил 746 входных и 79 выходных токенов. Это наблюдение одного запроса, не обещание задержки для всех вызовов.

Читайте ответ по слоям. `choice` говорит, какой вариант выбран; `probabilities` показывает распределение альтернатив; `score` относится к вашей шкале, `noul` к вашему утверждению. Поле `usage` описывает учтённые API токены и не даёт готовую стоимость всего workflow.

Для маленького эксперимента замените сообщение на «Экспорт PDF не работает; другой способ ещё не проверял». Сохраните оба запроса и ответа. Проверьте, какой вопрос изменился и соответствует ли это его формулировке. Важна правильность на размеченных примерах, а не рост `confidence`.

## 5. Что именно мы собираем

Теперь вернёмся к поиску в приложении задач. Контракт короткий:

```text
R1. Запрос «milk» находит карточку «Buy milk»: слово есть в заголовке.
R2. Запрос «carton» находит ту же карточку: слово есть только в описании «Remember the blue carton».
```

Приложение намеренно маленькое, весь поиск помещается на экран:

```python
ITEMS = [
    {"id": 1, "title": "Buy milk", "description": "Remember the blue carton"},
    {"id": 2, "title": "Prepare slides", "description": "Explain the export feature"},
]

def api_search(query, fields):
    query = query.casefold()
    return [item for item in ITEMS
            if any(query in item.get(field, "").casefold() for field in fields)]

def ui_request(query):
    return {"query": query, "fields": ["title"]}

def search(query):
    request = ui_request(query)
    return api_search(request["query"], request["fields"])
```

Backend умеет искать по обоим полям, а построитель запроса из интерфейса передаёт только `title`. Отдельный сервер и браузер не нужны, поэтому проверки воспроизводятся одной командой.

Наш исходный случай: worker утверждает, что поиск готов, а в журнале есть только успешная проверка R1. Требование R2 ещё не подтверждено. В демонстрационной реализации скрыта ошибка: запрос из интерфейса ограничивает поиск заголовком.

Проверки делятся на две группы. C1 и C2 образуют обязательную приёмку, код запускает их сам по заранее известной связи с требованиями. D1 и D2 дают дополнительную диагностику, и её ещё нужно выбрать. Вот здесь и появляется место для Choice: какое наблюдение сейчас полезнее получить?

```text
R1  требование            поиск находит карточку по слову из заголовка
R2  требование            поиск находит карточку по слову только из описания
C1  обязательная проверка search("milk")   ожидает карточку 1
C2  обязательная проверка search("carton") ожидает карточку 1
D1  диагностика           зовёт backend напрямую по обоим полям
D2  диагностика           показывает, какие поля передал интерфейс
```

![Три инструмента и роли Jev, проверок и программной политики](./assets/03-three-builds.svg)

Роли в системе простые. Worker пишет изменения. Инструменты исполняют проверки и собирают факты. Jev отвечает на узкие смысловые вопросы. `policy` остаётся обычной функцией: она определяет разрешённый следующий шаг и условие остановки. Всю эту обвязку агента обычно называют harness.

Если ваш проект уже покрыт точными дешёвыми тестами, запустите их. В нашем игрушечном поиске тоже можно обойтись без Jev. Смысл сборки в том, чтобы получить место для подключения семантической оценки и проверить, нужна ли она на более сложных материалах вашего проекта.

Первый полный запуск:

```bash
python3 run.py loop --mode demo --case missing-evidence --out runs/first-loop
```

После него останутся `run-report.md`, состояние `state.json`, события `events.jsonl` и записи вызовов judge. [Сохранённый пример отчёта](./jev-harness-lab/runs/example/run-report.md) уже есть в комплекте.

## 6. Сборка №1. Отчёт: что действительно подтверждено

Первая сборка решает самостоятельную задачу: разобрать уже выполненную работу. Вход: требования, версия кода, результаты проверок и отдельно сообщение worker. Выход: `evidence-report.json` для программы и `evidence-report.md` для человека.

```bash
python3 run.py evidence --mode demo --case missing-evidence --out runs/evidence-demo
```

Прежде чем спрашивать Jev, зададим смысл статусов:

- `passed`: актуальная зарегистрированная проверка подтверждает критерий.
- `failed`: актуальная проверка обнаружила нарушение.
- `unverified`: подтверждения недостаточно; например, проверку не запускали или результат относится к старому коду.

Сообщение worker «всё готово» сохраняется как утверждение автора изменений. Оно не превращается в результат теста.

### Сначала происхождение факта, затем его смысл

У результата проверки должен быть источник: ID проверки, команда, код завершения, вывод, время и снимок проекта. Вот настоящая запись провалившейся C2 из живого прогона раздела 10, хеши сокращены, служебные поля опущены:

```json
{
  "check_id": "C2",
  "snapshot": "d8fd8d95…fc7408",
  "snapshot_after": "d8fd8d95…fc7408",
  "exit_code": 1,
  "stdout": "{\"check_id\": \"C2\", \"kind\": \"assertion_failure\", \"detail\": \"description-only search: expected [1], got []\"}"
}
```

Снимок берётся дважды, до и после запуска: проверка не должна менять проект, и равенство двух хешей это подтверждает.

Если после проверки изменился код, зелёный результат нельзя автоматически перенести на новую версию. Сопоставление хешей делает программа. Jev не нужно просить сравнивать строки хешей, считать попытки или определять, равен ли exit code нулю.

В учебном проекте связь C1 → R1 и C2 → R2 известна заранее. Для неё достаточно реестра. Смысловая оценка появляется, когда к требованию относятся материалы без такой точной привязки: описание чужого теста, фрагмент отчёта, наблюдение из ручного прогона.

### Какой вопрос задать Jev

«Задача выполнена правильно?» объединяет слишком многое: требования, полноту тестов, исполнение, текущую версию и качество реализации.

Вместо этого возьмём одну пару: критерий R2 и описание чужого теста, которого нет в нашем реестре. Допустим, из соседнего набора пришла строка «test_search_keyword: вызывает `search("milk")` и проверяет, что вернулась карточка 1». Передадим Jev только материал этой пары и спросим:

```python
question = {
    "type": "noul",
    "instructions": (
        "Проверяет ли описанный тест поиск записи, в которой "
        "запрос присутствует только в описании?"
    ),
    "criteria": {
        "true": "Сценарий явно исключает совпадение запроса с заголовком",
        "false": "Сценарий проверяет только заголовок или не исключает совпадение с ним",
    },
}
```

Jev оценивает связь описания теста с критерием. На примере выше ожидается низкий Noul: тест ищет слово из заголовка, а R2 требует совпадения только в описании. Запуск теста и его результат это другой слой. Даже высокий Noul не доказывает, что тест исполнялся, прошёл или проверяет актуальную версию. В живых прогонах раздела 10 бесспорная пара C1 → R1 получала Noul 0.88–0.91: единицу модель не ставит даже там, где спорить не о чем.

В нашей сборке семантическая оценка остаётся отдельной аннотацией. Она помогает разбирать материалы, но не повышает обязательный критерий до `passed`. Для допуска к завершению используется явная карта приёмки. Так читатель может сначала оценить ошибки Jev на своих отчётах, прежде чем расширять его влияние.

У этой границы есть проверенная деталь: если API недоступен во время такой необязательной Noul-аннотации, отчёт сохранит `scope_annotation_error`, а свежие результаты C1/C2 продолжат определять приёмку. Ошибка обязательного Choice-маршрутизатора обрабатывается иначе: цикл останавливается. Вызов, который влияет только на пояснение, не должен незаметно становиться условием работоспособности всей системы.

Практическая логика статуса короткая:

```python
# runner возвращает 0 при успехе, 1 при провале assertion, 2 при ошибке инструмента
PASSED, FAILED = 0, 1

def is_fresh(check, current_snapshot):
    # снимок берётся до и после запуска: сама проверка не должна менять проект
    return (check["snapshot"] == current_snapshot
            and check["snapshot_after"] == current_snapshot)

def requirement_status(current_snapshot, latest_check):
    if latest_check is None:
        return "unverified"
    if not is_fresh(latest_check, current_snapshot):
        return "unverified"
    if latest_check["exit_code"] == PASSED:
        return "passed"
    if latest_check["exit_code"] == FAILED:
        return "failed"
    return "unverified"   # код 2, таймаут, упавший runner
```

Это сокращённое объяснение правила; полная реализация и формат записей находятся в `evidence.py`. Обратите внимание на последнюю ветку: сломавшийся инструмент не считается ни подтверждением, ни опровержением. Свежесть также зависит от версии самих проверок: комплект сохраняет и сверяет хеш их контракта. В другом проекте соглашение об exit codes нужно определить отдельно.

Отчёт не должен придумывать рассуждения от имени Jev. Модель вернула число; текст вроде «C2 не выполнялась на текущей версии» создаёт программа на основании журнала. В результате читатель видит не загадочный вердикт, а проверяемую связь между требованием, фактом и правилом.

Самостоятельный продукт уже готов: такой отчёт можно открыть перед review, даже если исправление будет делать человек.

Чтобы разобрать сохранённый запуск без новых проверок, подайте его состояние:

```bash
python3 run.py evidence --mode demo \
  --state runs/first-loop/state.json --out runs/saved-report
```

В этом режиме записи из файла считаются доверенными данными пользователя: хеши проверяют их актуальность, но не удостоверяют подлинность. Формат пока рассчитан на учебные C1/C2; для своего проекта нужно перенести и реестр, и соответствующие проверки.

## 7. Сборка №2. Какую проверку запустить следующей

Во второй сборке входом становится неполный или неуспешный отчёт, а выходом становится `next-check.json`: конкретный ID проверки и основание решения программы.

```bash
python3 run.py next-check --mode demo --case missing-evidence --out runs/router-demo
```

Если C2 обязательна и ещё не выполнена, её назначает код. Вызывать Jev для этого выбора бессмысленно: нужное действие уже записано в контракте.

Теперь C2 выполнилась и упала. Нужно локализовать причину. В реестре есть:

```python
diagnostics = {
    "D1": "Выполнить поиск по описанию напрямую через backend",
    "D2": "Посмотреть, какие поля поиска передаёт интерфейс",
    "none_suitable": "Ни одна доступная проверка не даст полезного нового факта",
}
```

В этой реализации Jev получает требование, запись актуального провала, описание архитектуры и доступных проверок. Его задача сформулирована через ожидаемую информацию:

```python
next_check_question = {
    "type": "choice",
    "instructions": (
        "Какая доступная диагностика даст наиболее полезный новый факт "
        "для локализации наблюдаемого сбоя?"
    ),
    "criteria": diagnostics,
}
```

Плохой вариант выглядит так: «выбери лучший тест» с названиями `test_1` и `test_2`. Модель не знает, что внутри этих команд. Хорошее описание сообщает, какой вопрос разрешает каждая проверка.

Приложение читает `choice`, сохраняет распределение и сверяет ID с разрешённым реестром. Команду оно берёт из своей конфигурации. Текст ответа модели никогда не исполняется как shell.

```python
selected = answer["choice"]
if selected == "none_suitable":
    action = "stop_for_review"
elif selected not in allowed_check_ids:
    action = "stop_invalid_answer"
else:
    action = "run_registered_check"
```

В подготовленном demo выбран D2. Его реальный локальный запуск показывает, что интерфейс передаёт только поле `title`. Теперь у worker есть полезная дополнительная информация: в какой части пути проявляется ограничение. В `live` Jev может предпочесть D1, отказаться от выбора или ошибиться. Журнал должен сохранить именно фактическую ветку.

Порог `confidence`, если вы его используете, задаётся в policy. Это ваш параметр, который нужно подобрать на размеченных случаях. Число вроде `0.8` без такой проверки не означает «достаточно безопасно» или «80% правильных решений».

У маршрутизатора есть простой конкурент: выполнить все проверки. Когда D1 и D2 стоят миллисекунды, конкурент вполне может выиграть. Selector становится интереснее при дорогих или многочисленных диагностических действиях, но этот выигрыш ещё предстоит измерить.

## 8. Сборка №3. Цикл, который умеет остановиться

Третья сборка соединяет получение фактов, вопросы Jev и worker. После каждого изменения повторяется приёмка текущей версии. Любая остановка получает явную причину.

![Путь подготовленного offline demo: непроверенный R2, провал C2, диагностика D2, исправление и новая приёмка](./assets/04-run-trace.svg)

У процесса несколько разрешённых действий: запустить обязательную проверку, получить дополнительное наблюдение, передать сбой worker, завершить по контракту или остановиться для разбора.

Правила стоит выписать словами:

1. Если обязательное подтверждение отсутствует или устарело, выполнить соответствующую проверку.
2. Если проверка обнаружила нарушение, при необходимости получить дополнительный факт и передать worker воспроизводимый сбой.
3. Если все обязательные критерии подтверждены для текущей версии, завершить по этому контракту.
4. Если изменений нет, подходящей диагностики нет либо лимит исчерпан, сохранить состояние и остановиться с причиной.
5. Если обязательный Choice недоступен, невалиден или недостаточно уверен, остановиться с причиной. Ошибка необязательной Noul-аннотации сохраняется отдельно. Продолжить по другой политике можно явным новым запуском; ошибка API никогда не подтверждает готовность.

Высокая модельная оценка не может отменить провал C2. Решение `complete` означает ровно выполнение описанного контракта приёмки; два теста не доказывают отсутствие всех возможных дефектов.

### Что передать worker на исправление

Вместо «попробуй ещё раз» передайте минимальный пакет:

```text
Критерий: R2 — поиск находит запись по описанию.
Воспроизведение: зарегистрированная проверка C2.
Результат: ожидаемая запись не найдена.
Дополнительное наблюдение D2: запрос содержит fields=["title"].
Область исправления: код приложения; контракт приёмки сохраняется.
После изменения: повторить C1 и C2 на новом снимке.
```

Это форма задания на исправление, а не сгенерированное Jev объяснение. Каждый факт должен иметь ссылку на запись инструмента. В demo исправление детерминированное: worker меняет известную ошибку. В `live` такую же информацию получает coding agent, и результат заранее неизвестен.

После изменения нужен новый snapshot. Старые PASS и FAIL остаются историей; текущую готовность определяют свежие результаты. Если worker вернул громкий отчёт, но файлы не изменились, цикл не должен бесконечно перепроверять одно и то же.

### Зачем разделять три сборки

Так проще понять, что именно сломалось. Ошибочная связь evidence с требованием относится к первому инструменту. Бесполезная диагностика относится ко второму, продолжение без прогресса или неверное завершение к третьему. Улучшать весь процесс одним длинным prompt намного труднее: меняются сразу несколько неизвестных.

Такая архитектура уже обсуждается в проектах вокруг Jev. Например, [Foreman](https://github.com/thruwire/foreman) отделяет worker от управляющих решений. Наш следующий шаг: наблюдаемые запуски и сравнение с простыми правилами.

## 9. Подключаем настоящий coding agent и Jev

В качестве worker используем Codex CLI. Он получает задачу, фактический провал и диагностику, читает `app.py` и вносит изменение. После этого harness повторяет проверки самостоятельно: ответ агента не определяет итог приёмки.

Для автоматического запуска подходит `codex exec`. Наш адаптер читает JSON-события в процессе исполнения, проверяет завершение хода и забирает итоговое сообщение через `--output-last-message`. Используется текущая настроенная модель CLI. Рабочая копия ограничена каталогом `runs/.../project`, а изменение разрешено только в `app.py`. [Документация неинтерактивного Codex](https://developers.openai.com/codex/noninteractive).

Настройте доступ Codex обычным способом и создайте локальную конфигурацию:

```bash
codex --version
codex login status
python3 adapters/codex_cli.py --configure
```

Последняя команда создаёт `worker-config-codex.json` и `policy-codex.json` с путями вашей установки. В нашем прогоне использовалась CLI `0.155.0-alpha.9` с авторизацией ChatGPT. Для проверки самого цикла начнём с фиксированного выбора диагностики:

```bash
python3 run.py loop --mode live --selector fixed \
  --case missing-evidence --task task.md \
  --worker-config worker-config-codex.json \
  --policy policy-codex.json \
  --out runs/my-codex-run
```

Этот запуск выполняет реальные действия worker. Вариант `fixed` выбирает D1 программно и не вызывает Jev. Так мы проверяем, что код действительно доходит до coding agent, изменяет приложение, повторно проверяет результат и умеет завершить цикл.

Чтобы передать выбор диагностики Jev, настройте `TYPESAFE_API_KEY` и замените `--selector fixed` на `--selector jev`:

```bash
python3 run.py loop --mode live --selector jev \
  --case missing-evidence --task task.md \
  --worker-config worker-config-codex.json \
  --policy policy-codex.json \
  --out runs/my-jev-codex-run
```

Jev отвечает за вопросы первых двух сборок, Codex за изменение кода. Ключ TypeSafe не передаётся в процесс worker. Таймаут одной попытки Codex равен 90 секундам; внешний supervisor ограничивает её вместе с дочерними процессами. Политика допускает до двух исправлений и 300 секунд на весь цикл. Фактические токены worker сохраняются отдельно от usage Jev: это разные расходы.

Сам адаптер использует `workspace-write`, запрещает запросы на повышение прав и отключает веб-поиск. После завершения он проверяет, что вне `app.py` ничего не изменилось.

Если вы используете другого исполнителя, замените адаптер, сохранив протокол. Stdin принимает один JSON с `task`, `project`, `feedback`, `iteration`; stdout возвращает:

```json
{"claim": "Краткое описание сделанных изменений"}
```

Ненулевой exit code, невалидный ответ или таймаут дают остановку с причиной. Полный адаптер находится в `adapters/codex_cli.py`; совместимый пример для Claude Code также оставлен в комплекте.

## 10. Читаем запуск как цепочку фактов

В успешном offline-сценарии маршрут такой:

```text
C1: PASS — поиск по заголовку работает.
R2: UNVERIFIED — текущего результата C2 ещё нет.
C2: FAIL — запись по одному описанию не найдена.
Jev demo fixture: D2 — подготовленный выбор диагностики.
D2: запрос ограничен полем title.
Demo worker: исправляет перечень полей.
Новый snapshot.
C1: PASS; C2: PASS.
Policy: COMPLETE — текущий контракт приёмки выполнен.
```

Здесь пять настоящих запусков проверок и одно подготовленное исправление. Эта трасса показывает работу программы. Она не показывает, что живой Jev выбрал бы D2 или что живой worker исправил бы ошибку за одну попытку.

Запустите ещё два случая:

```bash
python3 run.py loop --mode demo --case correct --out runs/correct
python3 run.py loop --mode demo --case stalled --out runs/stalled
```

`correct` начинает с исправной реализации. Нужный результат: подтверждённая приёмка без лишнего исправления. `stalled` возвращает уверенное сообщение worker, но оставляет файлы прежними. Нужный результат: остановка по отсутствию изменений, с сохранённым провалом. Она полезнее бесконечной последовательности «попробуй ещё».

Ошибка самого harness может завершить работу ложным успехом не хуже ошибки модели, поэтому он тоже покрыт тестами:

```bash
python3 -m unittest discover -s tests -v
```

Они проверяют успешный путь и крайние случаи: устаревшее evidence, неподходящий вариант диагностики, повреждённый ответ judge, ошибку API, ранний `sys.exit(0)` из приложения, смену контракта, незавершённый ход worker, фоновые процессы и исчерпание бюджета.

### Теперь тот же harness с настоящим Codex

Мы зафиксировали три исходных дефекта до запуска, затем по очереди передали их настоящему Codex. Диагностику выбирал `fixed`, чтобы отдельно проверить работу исполнителя и приёмки:

- **Только интерфейс:** запрос терял поле `description`. Одно исправление, пять проверок; финальная независимая приёмка пройдена. Полное время 15,17 секунды.
- **Только backend:** интерфейс передавал оба поля, но backend читал лишь заголовок. Одно исправление, пять проверок; независимая приёмка пройдена. 17,02 секунды.
- **Оба дефекта:** ограничение было в интерфейсе и backend одновременно. Одно исправление, пять проверок; независимая приёмка пройдена. 20,43 секунды.

Это три настоящих изменения кода, по одному прогону на случай. После остановки отдельный процесс проверил ещё четыре запроса: два совпадения по описанию, верхний регистр и отсутствие совпадений. Ни один из этих результатов не возвращался worker во время работы. Ложных `complete` в этих трёх опытах не было.

Исходные файлы, SHA256, результаты и usage сохранены в [протоколе опыта](./verification/codex-worker-2026-09-19/evaluation.md). Время включает всю цепочку и финальную проверку, а не только генерацию модели. Jev в этом опыте не вызывался: вклад selector измеряется отдельно.

Воспроизведение после настройки Codex:

```bash
python3 worker_eval.py --out runs/my-worker-evaluation
```

Команда выполняет три реальные задачи; понадобятся авторизация Codex и доступный лимит аккаунта. Всего в наборе 83 проверки, включая отказ необязательного judge, неполный учёт токенов и перенос сохранённого проекта. [Локальный журнал](./verification/terminal/unit-tests-83.txt) сохранён; CI гоняет тесты на Python 3.9, 3.12, 3.13 и 3.14 и отдельно проверяет воспроизводимую сборку HTML.

### Что изменилось, когда диагностику выбрал настоящий Jev

Затем мы снова создали три исходных дефекта и запустили `--selector jev`. Код и входы зафиксированы в manifest до первого вызова. На этот раз семантические аннотации и выбор диагностики действительно делал `jev-1.13.0`, а изменения вносил настоящий Codex:

```bash
python3 worker_eval.py --selector jev --out runs/my-jev-worker-evaluation
```

- **Дефект интерфейса:** Jev выбрал D2; одно исправление, пять проверок, независимая приёмка PASS. Весь опыт занял 20,98 секунды.
- **Дефект backend:** выбран D2, но `confidence=0.52` ниже зафиксированного порога `0.60`. После двух обязательных проверок система остановилась; worker не запускался. Независимая проверка подтвердила, что дефект остался. 2,17 секунды.
- **Оба дефекта:** выбран D2; одно исправление, пять проверок, независимая приёмка PASS. 21,57 секунды.

Итог первоначального опыта: **два автоматических завершения и одна остановка**, без ложных `complete`. Это более полезный результат, чем обещание, что добавление judge автоматически улучшает любой workflow. Вариант `fixed` ранее исправил все три подготовленных дефекта; на этих примерах преимущество Jev не установлено.

У всех чисел выше есть общее ограничение, и оно касается не только нашей выборки. В запросе нет ни `seed`, ни `temperature`: одинаковый запрос может вернуть другие вероятности. Собственные замеры TypeSafe на 15 повторах дают среднее стандартное отклонение вероятности около 0.01, а метка Choice у них переезжала на двух вопросах из восьми. Наш порог `0.60` и наблюдённые 0.52 лежат в той же узкой полосе. Прежде чем ставить порог в свой код, прогоните один и тот же запрос десяток раз и посмотрите, насколько гуляет ответ.

![Скриншот полного цикла: два исправления, остановка по confidence и отдельное восстановление](./assets/screenshots/03-live-loop-and-recovery.png)

*Сохранённые [результаты всех трёх запусков](./verification/jev-live-2026-09-20/codex-matrix/evaluation.md). Распределения по трём прогонам: D2 0.85 при `confidence` 0.77, D2 0.80 при 0.70 и D2 0.68 при 0.52. Последнее и есть остановка. Это одно число, записанное дважды: `(3 × 0.68 − 1) / 2 = 0.52`. Кандидаты при этом не были близки, D1 получил всего 0.26. Просто распределение стало площе в том случае, где дефект сидел в backend и прямой вызов через D1 годился не хуже, чем осмотр интерфейса через D2.*

### Как продолжить после такой остановки

Мы сохранили исходный неуспешный опыт, скопировали его состояние и явно выбрали `all`: выполнить обе доступные диагностики, затем передать факты worker. Порог Jev при этом не менялся. Новый запуск выполнил четыре проверки и одно исправление, независимая приёмка прошла; дополнительных запросов Jev было ноль. [Протокол восстановления](./verification/jev-live-2026-09-20/backend-recovery/recovery.json), [вывод команды](./verification/terminal/backend-recovery.txt).

Для собственного запуска сначала сохраните отдельную копию матрицы, затем продолжите из нужного состояния. Пример для такого же остановленного backend-случая:

```bash
cp -Rf runs/my-jev-worker-evaluation runs/my-jev-worker-recovery
python3 run.py loop --mode live --selector all \
  --state runs/my-jev-worker-recovery/backend-title-only/state.json \
  --out runs/my-recovery-result \
  --worker-config worker-config-codex.json --policy policy-codex.json
```

Состояние содержит относительную ссылку на проект и записи уже выполненных проверок. Поэтому две свежие обязательные проверки из предыдущего запуска можно прочитать, а после изменения кода выполнить их заново. Неизвестный новый дефект может дать другой итог; сохраните его так же, как успешный.

Из этого опыта получается практическое правило: заранее определите, что делать при неуверенном выборе. Для двух дешёвых локальных диагностик разумно явно запустить обе. Для дорогого внешнего действия может требоваться человек. **Остановка и способ продолжить это часть продукта, который вы собираете.**

![Скриншот сохранённого протокола автоматических тестов и команд](./assets/screenshots/04-tests-and-terminal.png)

*Просмотр фактического вывода команд в локальной галерее. Полные текстовые журналы и исходные JSON приложены рядом; изображение не заменяет их.*

### Replay: меняем правило на сохранённой записи

Replay читает сохранённые входы и ответы, заново рассчитывает действия policy и не вызывает модели:

```bash
python3 run.py replay --run runs/first-loop --policy policy.json
```

С исходной policy последовательность должна совпасть. Скопируйте настройки в другой файл и уменьшите, например, бюджет проверок. Replay покажет первое действие, которое теперь отличается.

После этого расхождения нельзя продолжать выдавать старую запись за новый эксперимент. Если другая policy выбрала D1 вместо D2, последующие исправления и ответы в старом журнале относятся к другой истории. Для новой траектории нужен новый запуск. Replay полезен для аудита правил; качество нового поведения измеряется реальным rollout.

## 11. Как проверить, нужен ли вам Jev

Работающий код отвечает на вопрос «собрали ли мы систему». Польза Jev требует другого сравнения.

Начните с одного узла, например с выбора дополнительной диагностики. Соберите сохранённые состояния после реальных провалов: критерий, свежий результат, уже известные факты и доступные проверки. Для каждого состояния определите, какие проверки действительно дают полезную новую информацию. Иногда правильный ответ в том, чтобы выполнить всё, иногда в том, чтобы остановиться и расширить инструменты.

Часть случаев используйте для настройки вопросов и порогов; другую часть отложите до окончания настройки. Включите простые примеры, неоднозначные описания, нерелевантные материалы и случаи без подходящего кандидата. Не превращайте три учебных fixture в статистический benchmark.

Сравните три варианта на одинаковом наборе:

- **Фиксированный порядок.** Та же приёмка и те же доступные инструменты; дополнительные проверки идут по заранее заданному списку.
- **Все проверки.** Запускается весь допустимый набор; его дополнительное время и стоимость учитываются явно.
- **Choice Jev.** Та же приёмка и тот же бюджет, но дополнительный шаг выбирает модель.

Для чистого сравнения selector передавайте всем вариантам один и тот же подготовленный отчёт. Если одновременно поменять и отчёт, и selector, получим сравнение двух целых политик, и уже не сможем приписать разницу одному Choice.

В комплекте эта схема запускается на учебных случаях:

```bash
python3 run.py loop --mode demo --selector fixed --out runs/fixed
python3 run.py loop --mode demo --selector all --out runs/all
python3 evaluate.py --out evaluation-local
```

`fixed` и `all` полностью обходятся без Jev, включая Noul-аннотации. `evaluate.py` выполняет девять offline-прогонов: три подготовленных случая × три политики, затем отдельную финальную приёмку. Это воспроизводимая проверка механики сравнения; детерминированный demo-worker исправляет известную ошибку независимо от D1/D2, поэтому из этой матрицы нельзя получить доказательство пользы selector.

Мы выполнили отдельный зафиксированный набор: 18 состояний и 28 решений. В нём десять обращений на русском и английском для Choice/Noul и восемь диагностических ситуаций для D1/D2/`none_suitable`. Эталонные метки не передавались модели. Вызов сохраняет сырой ответ, версию, usage, длительность и отдельно учитывает ошибку выбора, отказ по неуверенности и корректный `none_suitable`:

```bash
python3 live_eval.py --out runs/my-jev-evaluation
```

Результат: **28 правильных ответов из 28**: категория 10/10, рабочий обход 10/10, следующая диагностика 8/8. Политика приняла все ответы; два правильных результата были `none_suitable`. Получены 18 ответов API без ошибок; суммарное время запросов 17,10 секунды, usage 9 322 входных и 1 024 выходных токена. Это данные [первого протокола](./verification/jev-live-2026-09-20/primary-eval/report.md).

Затем отдельно составлен **второй набор из 18 новых случаев**, без просмотра его будущих ответов и без изменения вопросов или порогов. В нём есть отрицания, непроверенные советы, ключевые слова в названиях карточек, текстовые попытки переопределить категорию, устаревшие snapshot и уже исполненные диагностики. [Методика составления](./jev-harness-lab/challenge-method.md).

```bash
python3 live_eval.py \
  --cases fixtures/live-eval-challenge-cases.json \
  --out runs/my-jev-challenge
```

И здесь получены **28 правильных ответов из 28**, все приняты политикой; три правильных `none_suitable`, без ошибок API. 18 запросов заняли суммарно 17,26 секунды, usage 10 824 входных и 1 026 выходных токенов. [Второй протокол](./verification/jev-live-2026-09-20/challenge-eval/report.md).

![Скриншот результатов двух отдельных размеченных наборов Jev](./assets/screenshots/02-live-evaluations.png)

Наборы небольшие и подобраны авторами. Они подтверждают, что эти запросы и ответы работают на перечисленных случаях; они не устанавливают надёжность на вашем трафике, качество калибровки или защиту от произвольной текстовой инъекции. Score проверен в первых прямых вызовах, но в эти две accuracy-оценки не входит. Слабые контрольные правила тоже сохранены: поиск ключевых слов, постоянное «обхода нет» и постоянный D1. Они полезны как прозрачная отправная точка, но не заменяют сильную LLM-базовую линию.

Именно поэтому нужна ещё проверка всей цепочки. В размеченном диагностическом состоянии обычно был один явно полезный шаг. В реальном loop при провале C2 обе диагностики могли оказаться полезны, и один неуверенный выбор остановил ремонт. **Правильные ответы на отдельном наборе и успешное завершение задачи это разные показатели.**

Что считать? Сначала качество: ложные завершения, неподтверждённые требования и независимая итоговая приёмка. Затем издержки: лишние вмешательства, число проверок, попытки worker, полное время и расходы всей цепочки. Быстрый вызов judge может привести к лишней дорогой итерации; это станет видно только при подсчёте всего запуска.

Финальная оценка должна происходить после остановки. Её дополнительные тесты или экспертные ответы не передаются worker и selector в ходе сравниваемого запуска. Иначе вы дадите системе подсказку, по которой затем объявите её успешной.

Есть и отдельная проверка Noul: размеченные пары «требование и описание свидетельства». Замерьте, как часто модель считает нерелевантный материал подтверждением. Если эта оценка когда-нибудь начнёт влиять на приёмку, цена такого ложного подтверждения обычно важнее красивого среднего результата.

Документация Jev 1.13 перечисляет девять слабых мест. Четыре касаются нашей сборки прямо: буквальное прочтение условий, ошибки на точном счёте и сравнении дат, ухудшение при лишнем контексте, влияние вводящих в заблуждение материалов. Ещё два стоит держать в голове отдельно, потому что наш собственный Noul-критерий построен на отрицании: модель хуже читает двойные отрицания с косвенными формулировками и путается, когда критерии внутри одного вопроса противоречат друг другу. Поэтому вопрос о смысловой связи стоит делать узким, а точные вычисления и инварианты оставлять коду. [Описанные ограничения Jev 1.13](https://docs.typesafe.ai/model-jaggedness/jev-1.13).

Для первого внедрения достаточно режима наблюдения: Jev предлагает решение, действующая система выполняет своё, вы сохраняете расхождения. Разбирайте отдельно полезные изменения и регрессии. После этого будет понятно, какое конкретное действие можно передать модели и с какими условиями остановки.

## 12. Что забрать в свой проект

Перенос начинается с одного требования. Например: «При изменении поискового запроса сохраняется выбранный фильтр». Добавьте ему ID, опишите обязательную проверку и определите, какие дополнительные наблюдения помогут локализовать возможный сбой. Только после этого сформулируйте вопросы Jev.

Практически это означает согласованно изменить `task.md`, `CRITERIA` в `evidence.py`, записи `checks.json`, исполняемые проверки в `check_runner.py` и независимую приёмку. Один новый текст в `--task` не создаёт новый проверочный контракт автоматически.

В state передайте короткие материалы по этому требованию, их происхождение и текущую версию. В Noul спросите о конкретной связи. В Choice опишите, какой новый факт приносит каждая диагностика, и оставьте `none_suitable`. Если нужна приоритизация нескольких проблем, добавьте Score с различимыми уровнями. Объедините ответы обычной функцией policy.

Файлы комплекта распределены по этим ролям:

```text
jev-harness-lab/
  run.py                  команды и соединение этапов
  evaluate.py             offline-матрица трёх политик
  judge.py                вопросы, TypeSafe HTTP API, demo-ответы
  evidence.py             факты, снимки, отчёты по требованиям
  policy.py               допустимые действия и остановка
  worker.py               протокол исполнителя
  checks.json             реестр проверок
  policy.json             пороги и лимиты
  task.md                 задача и контракт приёмки
  demo-project/           маленькое приложение с поиском
  adapters/codex_cli.py    проверяемый live-адаптер Codex
  worker_eval.py          три реальных опыта с coding agent
  live_eval.py            размеченная проверка решений Jev
  tests/                  проверки самого harness
```

Начните с того продукта, который нужен сейчас. **Evidence report** пригодится перед ручным review. **Next-check router** поможет организовать диагностику. **Bounded loop** свяжет их с исполнителем и сохранит причину остановки.

Хороший следующий шаг после этой статьи: взять один настоящий провал своего агента, получить из него `state`, задать один узкий вопрос Jev и сравнить ответ с решением по простому правилу. У вас останутся запрос, фактический результат и понятный критерий полезности. На такой основе уже можно решать, какую часть работы поручить модели.
